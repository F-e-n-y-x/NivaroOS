# HTTPS on the home network (audit M4)

On the LAN the dashboard and API are plain http, so a Wi-Fi sniffer sees the
password, the tokens and the companion secret. Tailscale (WireGuard, plus the
existing "HTTPS on the tailnet" switch, commit e353823d) and the Cloudflare
tunnel (TLS at Cloudflare's edge, cloudflared dials the gateway over http on
the box) are already encrypted and are not changed.

## What the owner gets

Settings > Network & Sharing > "HTTPS on your network", default **off**.

1. Switch on: the gateway creates a private certificate authority for this
   box and starts serving https on port 443 next to http (http keeps working:
   the Android app, bookmarks, scripts, cloudflared).
2. "Trust this server" (`http://<box>/trust`, no sign-in needed): download
   the CA certificate, its SHA-256 fingerprint, and short steps for Windows,
   macOS, iPhone/iPad, Android and Firefox.
3. Once the dashboard has been opened over https (so this browser trusts it),
   a second switch "Send browsers to https" redirects top-level page loads.

## Gateway

- Files in `/var/lib/nivaroos/tls` (systemd `StateDirectory`, 0700): `ca.crt`,
  `ca.key`, `server.crt`, `server.key` (keys 0600). Nothing is created while
  the switch has never been on.
- CA: ECDSA P-256, 10 years, `MaxPathLen 0`, **name constraints** (critical):
  DNS `local`, `localhost`, `lan`, `home.arpa`, `internal` and the hostname;
  IPs 10/8, 172.16/12, 192.168/16, 100.64/10 (Tailscale), 127/8, fc00::/7,
  ::1. A device that trusts it can't be fooled by it for any internet site,
  even if the box's key leaks.
- Server cert: 365 days, SANs = hostname (if the CA permits it),
  `<hostname>.local`, `localhost`, and every interface address in the ranges
  above (docker/veth/bridge interfaces skipped). Checked every 5 minutes and
  at start: reissued when it expires within 30 days or when the name/IP set
  changed (DHCP moved the box). Same CA, so nothing needs re-trusting.
- Listener: `gateway.TLSPort` (default 443), same handler as http, HTTP/1.1
  only (WebSocket upgrades through the reverse proxy work exactly as on http),
  TLS 1.2+, sets `X-Forwarded-Proto: https`. Failing to bind is reported in
  Settings and never affects the http listener.
- Config in `gateway.ini`: `TLS`, `TLSPort`, `TLSRedirect` (all off by default).
- API (management server, proxied at `/v1/gateway/tls`):
  `GET /v1/gateway/tls` public status (enabled, running, port, redirect,
  fingerprint, expiry, error); `PUT` with a token `{enabled, redirect}`;
  `GET /v1/gateway/tls/ca.crt` (DER) and `/v1/gateway/tls/trust` public;
  `/trust` on the gateway redirects to the latter.
- Redirect (only when on and the listener runs): GET/HEAD with
  `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest` document (or absent), host
  covered by the cert, peer not the box itself (cloudflared, tailscale serve,
  local scripts). 302, never 301/308 and no HSTS, so switching it off later
  can't strand a browser. API calls, the app, WebSockets, iframes: never.

## Android app

- `ServerTrust`: CA certificates the user accepted, kept in secure storage,
  added to one process-wide `SecurityContext` (system roots + pinned CAs)
  installed through `HttpOverrides.global` - covers package:http, WebSockets,
  `Image.network`. Real chain + hostname checks, nothing is skipped.
- Trust on first use: when a server offers https (status says enabled) or an
  https address fails with a certificate error, the app downloads the CA,
  shows its fingerprint ("compare with Settings > Network on the server") and
  pins it only if the user accepts. Then it checks the https address with the
  pinned CA and switches the server to it. "Keep http" leaves everything as is.
- WebView (Host Desktop Smooth): an SSL error proceeds only when the page's
  certificate is byte-identical to the one a pinned-CA-verified Dart
  connection to the same host:port receives.
- Video (ExoPlayer can't use a runtime CA): played through a loopback relay
  in the app that fetches from the server with the pinned context.

## Not covered

- The server -> phone file server (`http://<phone>:8765`, companion secret):
  the phone would need its own certificate; separate item.
- A real public certificate on the LAN: use the Tailscale HTTPS switch (real
  Let's Encrypt cert on the tailnet name, nothing to install) or the tunnel.
- Browsers keep separate logins per origin: the first https visit asks to sign
  in once.
